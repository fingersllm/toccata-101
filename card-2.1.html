Kaspa script: the program every output carries

Every output carries a program. The spender supplies the first half, the node runs both halves on one stack, and the spend is good only if a single true is left at the end.

Card 1.1 called the thing attached to a UTXO its script public key. Card 1.4 said a node takes that program and runs it. Neither card said what running it means. Below are three real spends from Kaspa mainnet, replayed instruction by instruction, on the same stack the node uses.

The right hand column is the ceiling the node enforces. Toccata raised three of them and left the stack where it was.

A Kaspa script has no loops and no instruction that jumps backwards, so it always ends. The engine counts as it goes: at most 244 items on the stack at any moment, and a script that runs past its size limit, past its instruction limit, or uses a disabled instruction is refused. Every node runs the same bytes against the same transaction and reaches the same answer, which is why a lock on Kaspa does not depend on anyone being trusted.

The first half, the one the spender brings, may only put data on the stack. It cannot compute. Every decision belongs to the half the coin carries. A covenant is that same half written to look at the transaction trying to spend it, and to leave false when it does not accept what it sees. The instructions that let it look are card 2.2.

Sources

In rusty-kaspa, an input is checked by running two scripts in order on one stack: the input's signature script, then the script public key of the UTXO it spends. The signature script may contain only push instructions. After every instruction the engine refuses a stack deeper than MAX_STACK_SIZE = 244, and it refuses disabled and reserved instructions. At the end exactly one item must be left and it must be true, otherwise the errors are CleanStack, EmptyStack or EvalFalse (crypto/txscript/src/lib.rs, execute_inner, execute_script, check_error_condition). For a p address the engine saves the stack before the coin's half runs, checks that half on its own, restores the saved stack, takes the top item as a script and runs it (same file). The limits, each checked per script: 10,000 bytes before Toccata and 1,000,000 after, one stack item 520 bytes before and 1,000,000 after, instructions per script 201 before and 1,000,000 after, stack 244 either way (same file). The two standard locks are OpData32 key OpCheckSig and OpBlake2b OpData32 hash OpEqual, the hash being blake2b-256 of the revealed script (crypto/txscript/src/standard.rs). The 256 byte values, which of them are disabled and which are always illegal (crypto/txscript/src/opcodes/mod.rs). Read at release v2.0.1. The two transactions were read from api.kaspa.org on 12 September 2026: 60a2f205…f145914 created both outputs and 2436d2fc…501f3d spent the p address one. The page holds their real bytes. It does not verify the signature or compute the hash in your browser, it shows the values those two transactions actually carry, and for the third spend the blake2b-256 of the changed script.
